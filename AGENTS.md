# AGENTS.md — Memory Map

Guide for AI agents and new contributors. Read this before changing code.
Known problems and planned improvements are tracked in [REVIEW_FINDINGS.md](REVIEW_FINDINGS.md) by ID (for example `BUG-3`).
Check that file before "fixing" something that looks odd: it may already be catalogued, with a suggested fix. When you fix one, add a **Status** line to it and update its heading marker and index row (see the top of that file).
Database and schema rules live in `app/src/main/java/com/szabolcshorvath/memorymap/data/AGENTS.md`.
The design of media re-linking is documented in `SIGNATURE_FIX_PLAN.md` (despite the file name).

## What the app is

**Memory Map** is a single-module Android app (Kotlin, XML Views) for saving personal "memories" on a map.
- A **memory** (`MemoryGroup`) has a title, description, location, date range (or all-day), a marker colour (HSV), photos and videos, and optional **fragments**.
- A **fragment** (`data/MemoryFragment`, a Room entity — not an Android Fragment) is an extra location inside a memory, with an optional date range and its own colour. Its title comes from its group.
- Screens: **Map** (clustered markers, date filter, colour stats pie chart), **Timeline** (search, grouped by day), **Add/Edit** memory, **Settings** (Google sign-in, Drive backup and restore, colour presets, map preferences, re-link media, send logs). There is also a memory detail pager and a full-screen media viewer.
- All data is local (Room). Google Drive (`drive.file` scope) is used only for zip backups of the database file.

## Build and run

Local setup needs files that are **not** in git:
- `local.properties` — copy `local.properties.template`.
- `app/google-services.json` — the Firebase config (ignored by git).

> ⚠️ `local.properties` also holds the release signing passwords. `app/build.gradle.kts` reads only the keys it needs: `MAPS_API_KEY` goes to a manifest placeholder and `OAUTH_WEB_CLIENT_ID` to `BuildConfig`. To add a new value, wire it up explicitly in the same way. Never expose the whole file (for example with the Maps Secrets Gradle plugin), and never log `BuildConfig` fields.

- Without `MAPS_API_KEY` the map doesn't load and place search is turned off (tapping the map still works).
- Without `OAUTH_WEB_CLIENT_ID` the build still succeeds, and sign-in says it isn't set up.
- JitPack (`settings.gradle.kts`) only serves the `com.github.chrisbanes` group (PhotoView). A new JitPack dependency needs its group added there.
- `minSdk` is 34 (Android 14), the oldest version any user has. Code needs no version checks or fallbacks for older Android versions.
- Robolectric-based tests (`ColorUtilTest`, `MemoryGroupDaoTest`, …) run against `targetSdk 37` with Robolectric 4.17 (older versions could not start them). They need JDK 21 or newer.
- CI runs the unit tests and lint (`tests.yml`, JDK 21, which Robolectric needs for Android 15 and newer), and Detekt (`detekt.yml`) on every push and PR to master, and each fails the check. The UI test workflow (`ui-tests.yml`) runs only when started by hand: CI's fresh emulators lack Google's latest map renderer (see Tests). Run `./gradlew testDebugUnitTest detekt lintDebug` locally before pushing, and the UI tests (`scripts/ui-tests.sh`, see Tests) when a change touches the UI.
- Detekt only reports issues that aren't in `config/detekt/baseline.xml`. Fix new issues instead of adding them to the baseline; regenerate it (`./gradlew detektBaseline`) only after fixing listed ones, so they don't come back unnoticed.

## Architecture

### Navigation (`MainActivity`)
- No Navigation component. The four tab fragments (`MapFragment`, `TimelineFragment`, `AddMemoryGroupFragment`, `SettingsFragment`) and `PickLocationFragment` are **all added once** in `onCreate`, with tags (`XxxFragment.TAG`). Switching tabs runs `show()` + `RESUMED` on the target and `hide()` on the other tabs: one that has a view is capped at `STARTED` (paused, its view kept, so it comes back as it was left and the map isn't rebuilt), one never shown stays at `CREATED` (no view yet). The keyboard is closed whenever a screen is hidden.
  - After the activity is recreated (rotation, process death), every hidden screen goes back to `CREATED` (`releaseHiddenViews`), so only the shown one builds its view. A hidden screen may therefore have no view: keep restoring UI state from the ViewModel in `onViewCreated`.
  - A hidden screen with a view keeps collecting its flows (they run while `STARTED`), so it stays up to date. Anything the user should see happen (a scroll, a flash, a camera move, a message) waits until it is `RESUMED`.
- Detail screens use the back stack: `MemoryPagerFragment` is `add`ed over the shown screen, which is hidden at `STARTED` (`onMemoryClicked`), so Back returns to it as it was. `MediaViewerFragment` is added the same way over the pager, and `PickLocationFragment` is shown over the Add tab; the picker goes back to `CREATED` when it closes, so a second map doesn't stay in memory.
- Screens talk to the activity through **listener interfaces** that `MainActivity` implements (`MapListener`, `TimelineListener`, `MemoryFragmentListener`, `AddMemoryGroupListener`, `PickLocationListener`), attached in `onAttach`.
- Cross-tab actions (show on map/timeline, edit) call `selectTab(itemId)` and then a `request…` method on the target fragment (`requestFocusOnMemory`, `requestScrollToAndFlash`, `requestEditMode`). The fragment keeps the request in its ViewModel and handles it once the tab is shown (in `onResume`, or right away if it is already resumed; Edit as soon as the form has a view, since filling a hidden form shows nothing), so nothing depends on when the tab transaction runs. A request stays pending until handled, and a newer one replaces it. `MainActivity` looks the fragments up by tag each time instead of keeping references.

### State
- Screen ViewModels mostly hold plain `var` fields: UI state survives rotation but not process death. The exceptions are the Add form's draft (with the memory it edits) and the location picker's picked spot, which are kept in `SavedStateHandle`.
- The Add tab is both "new memory" and "edit memory". `AddMemoryGroupFragmentViewModel.hasUnsavedChanges` compares the form with how it was when last cleared or loaded for editing (call `markUnchanged` after filling it). An Edit request asks before it replaces unsaved changes (for the memory already being edited it keeps them), and switching to another tab closes an edit that has no changes (`closeUnchangedEdit`). A new field that a save stores must also go into `FormContent` (`fragment/FormContent.kt`, with its Bundle code), or changing it won't count as a change and process death will lose it. Its input gets `android:saveEnabled="false"` and is filled from the ViewModel in `onViewCreated`: Android would otherwise restore what it showed when the tab was last left, over a form cleared meanwhile (a save that finished on another tab). A save result is handled only while the tab is shown: one that finishes on another tab clears the ViewModel at once, and the kept view shows it when the tab is shown again.
- Preferences: a single DataStore named `"googleAuthDatastore"` (it holds all app prefs, not just auth). Keys and defaults are in `util/PreferencesKeys.kt`; the default map filter is in `util/DateFilterOption.kt` (stored by enum `name`).

### Media handling and re-linking (read `SIGNATURE_FIX_PLAN.md`)
- Picked media keep their **photo picker URI**, with `takePersistableUriPermission` (survives reboots, no `READ_MEDIA_*` needed). Android caps persisted grants at 512 and drops the oldest beyond that, so call `LocalMediaUtil.releaseUriGrantsIfUnused` when media is removed or re-linked to another URI. The Add form does it for photos picked in it that leave the form unsaved (removed, cleared, replaced by an edit), but never for media loaded for editing.
- The Add form opens the photo picker through `AppServices.mediaPicker` (the system's `PickMultipleVisualMedia`), so UI tests can replace it. A screen registers its launcher with it once, when it is created.
- Each `MediaItem` stores `deviceId` (the installation id), `fileSize`, `dateTaken` and `mediaSignature` = `"{size}_{md5(first 4 KB + last 4 KB)}"` (`MediaHasher`). The signature is computed once and kept on later saves; only re-linking to an edited version (below) replaces it.
- Each item also stores what the file was (`MediaDetails`): name, pixel size, MIME type, video length and a perceptual hash (dHash) as columns, and a 128 px thumbnail in `media_thumbnails`, keyed by signature. They are read while the file can be read: when the Add form saves new picks (media kept through an edit copy theirs from the saved rows, never through `FormContent`), when the missing-photo sheet replaces an item, and at start-up for older items (`MediaDetailsBackfill`, which also deletes unused thumbnails, only then). They are shown and used for ranking, never for linking on their own; the hash only orders suggestions ("Looks alike").
- `InstallationIdentifier` lives in `noBackupFilesDir` on purpose, so Auto Backup and device transfer don't copy it. Don't move it back into DataStore.
- An item needs re-linking if `deviceId != installationId` or `!isMediaValid` (metadata-only check). `LocalMediaUtil.verifyAndFixMediaItems` matches MediaStore candidates by exact size + signature and updates only `uri` and `deviceId` (`updateMediaLink`), and only while the row still has the URI and signature the run read (a restore during the run can reuse ids). If the signature finds nothing, `EditedPhotoRule` handles a photo edited in place after it was picked: it takes the MediaStore file whose id is in the item's local photo picker URI, if the item was saved by this installation and the file is of the same type with the same date taken to the millisecond, and the item then also takes that file's size and signature. Its old URIs' grants are released if no item uses them. It runs on cold start, after a restore, and from the "Re-link" buttons, always through `MediaRelinker.relink` (never call it directly): runs happen one at a time in `applicationScope`, so they outlive the screen, and requests made during a run share the next one. Each run checks every item again and returns how many are still missing; `hasMissingMedia` answers from the results it cached, so only new or changed items cost a query. Afterwards `deduplicateMediaItems` removes items of one memory that now point to the same photo (same signature), closes the `order` gaps and releases unused grants.
- Never "sweep" all persisted grants that the current database doesn't reference: after restoring an older backup, a newer backup may still need them. Release only the grants of media you just removed (`releaseUriGrantsIfUnused`).
- The "Send logs" zip is written to `cacheDir/logs/`, the only folder the `FileProvider` shares (`res/xml/file_paths.xml`). Keep anything else (backup temp files) out of it.
- "Send logs" also adds `relink_diagnostics.txt` (`RelinkDiagnostics`): why each unlinked item needs re-linking and which files on the phone are near it, with sizes, dates, owners and signatures. It is built when the logs are sent (re-link runs don't pay for it), only reads, and writes its own failure into the file so the logs still go out. Its checks mirror `needsRelink` and the matching rules (signature and `EditedPhotoRule`), so keep them in step.
- Media from another device is shown as an error tile (type, size, date) and is not loaded.
- Tapping a tile whose item needs re-linking opens `MissingMediaSheet` (in the memory screen's `childFragmentManager`, the item id in its arguments) instead of the media viewer. With full media access it re-links first, then suggests files of the same type taken around the same time (`NearbyMedia`). The user can use one, choose another photo or remove the item (`MissingMedia`). A replacement is not a re-link: `MediaItemDao.replaceMedia` writes the new file's URI, device, type, signature, size and date, keeping the item's id and place.

### Backup and restore (`backup/BackupManager.kt`, `SettingsFragment`)
- Backup: `PRAGMA wal_checkpoint(TRUNCATE)`, copy the database file (and the WAL if not empty) while holding a write transaction (a consistent snapshot), check the copy with `MemoryMapDatabase.withCheckedCopy` (the same open, migration and integrity checks a restore runs), then zip `database.sqlite` (+ `-wal` if still present) + `metadata.json` (`BackupZip`) and upload to the Drive folder "Memory Map Backups" as `MemoryMap_{Automatic|Manual}_Backup_<yyyyMMdd_HHmmss>.zip`. Older backups also contain `-shm`; restore ignores it.
- **Automatic backups** run in the background through WorkManager (`backup/AutomaticBackups.kt`). Every write (save, reorder, preset changes, undo, a final delete) calls `AutomaticBackups.schedule(context)`, which returns at once. It enqueues unique work (`ExistingWorkPolicy.REPLACE`), so a burst of changes leads to one upload 15 seconds after the last one, only with a network, and it survives the screen and the process. `AutomaticBackupWorker` calls `BackupManager.runAutomaticBackup`, which skips when nobody is signed in and otherwise runs `performBackup`. Network and Drive server errors are retried (up to 5 attempts, exponential backoff); missing consent and other errors are not. Settings shows the state as a small inline line (`AutomaticBackups.status`) and refreshes the backup list when a run finishes. Never call `performBackup` for automatic backups directly. Old backups are still never pruned (`DATA-4`).
- Backup and restore share one process-wide `Mutex` in `BackupManager`, so they run one at a time (callers wait for the running one). Each run uses its own temp directory in `cacheDir` (`BackupTempFiles`); leftovers from killed runs are deleted when the next run starts.
- Old backups are never deleted by the app (pruning was deliberately postponed, `DATA-4`). `listBackups` pages through all of them.
- Restore: download, extract only the known entries (`BackupZip`), check `metadata.json` and `database.sqlite` exist, reject backups from a newer database version (`BackupCompatibility`), open the extracted copy with `MemoryMapDatabase.withCheckedCopy` (migrations, schema and integrity checks; rejects a file SQLite would have to create from scratch), read every row (`DatabaseContents`), then replace the live database's contents in one transaction (`DatabaseContentsDao.replaceAll`). The live database is never closed or swapped, Room's Flows pick up the new data, and any failure leaves the current data untouched. The UI then re-links media with whatever media access was granted (the restore never waits for it) and offers full access if photos are still unlinked.
- Android's own Auto Backup and device transfer exclude the database and the DataStore (`res/xml/data_extraction_rules.xml`): memories come back only through the Drive backups.
- Auth: sign-in stores the email in DataStore (`USER_EMAIL_KEY`). Sign-in and Drive consent go through `AppServices.accounts` (`GoogleAccountService`: Credential Manager and `AuthorizationClient`), and Drive file calls through `AppServices.backupStorage` (`DriveBackupStorage`, which builds a `GoogleAccountCredential` from the email). Always reach them through `AppServices` at the time of the call, never directly: UI tests replace both with fakes, so a test never touches a real account.

## Conventions

- Run `./gradlew detekt` before committing (CI fails on new issues). `MagicNumber` is active, which is why numbers live in named `private const val`s in a `companion object`.
- In async callbacks use `val binding = _binding ?: return`, and `viewLifecycleOwnerLiveData.value ?: return` instead of `viewLifecycleOwner` (that getter throws when there is no view).
- Register activity result launchers as **property initializers**, never in `onCreateView`: views are recreated on every tab switch, so callbacks would pile up.
- The location itself is read through `AppServices.location` (`FusedLocationService`, Google Play services' fused provider), so UI tests can say where the phone is. The location picker's place search goes through `AppServices.placeSearch` (`GooglePlaceSearch`: the Places SDK's search screen and Place Details), so UI tests don't call the paid API. Location access is asked for only when the user taps a "my location" button (`util/MyLocationAction.kt`, used by the map and the location picker), never when a screen opens: first a short explanation, then the system dialog, and once Android no longer asks, an offer to open the app's settings (the denial is kept in DataStore, `LOCATION_PERMISSION_DENIED`). Google's own my-location button is turned off because it only appears once access is granted. Code that merely uses the location when it is granted (the blue dot, the first zoom, preselecting it in the picker) must not ask.
- Ask yes-or-no questions with `util/ConfirmDialog` (a DialogFragment), not a plain `AlertDialog`, which closes when the phone is turned. Show it in the fragment's `childFragmentManager`, listen for the answer in `onCreate` (`ConfirmDialog.listen`), and pass what the answer acts on in its `extras`: after process death the fragment's other state is gone.
- Material date and time pickers come back after a rotation without their listeners. Show each under a tag that says what it is for (unique within its `FragmentManager`) and attach its listener with `setOnPicked` when showing it, and again in `onViewCreated` with `reattachDatePicker` / `findTimePicker` (`util/PickerListeners.kt`). After process death a restored date picker ignores the dates tapped in it, so `reattachDatePicker` replaces it with a new one built from the same options. A picker for a list item identifies the item by a stable id, not its position.
- Firebase Performance is used heavily: `@AddTrace` annotations, `PerfUtil.trace("name") { }`, `RoomDatabase.withTransaction("name") { }` (the traced overload in `PerfUtil`). Trace names are `snake_case` (`<class>_<method>`). Don't put `@AddTrace` on hot or per-item functions (helpers called per marker, per pair or per media item): each call starts a trace.
- User-facing strings are currently hard-coded in Kotlin and XML (`I18N-1`). New code should prefer `strings.xml`.
- Read theme colours through theme attributes (`?attr/colorPrimary` in XML, `MaterialColors.getColor` in Kotlin), never `@color/md_theme_*` or `R.color.md_theme_*`. When the phone's contrast setting is raised, `MemoryMapApplication` applies the medium or high contrast overlay (`res/values/theme_overlays.xml`), which changes only the attributes.
- Generated or local-only files to keep out of commits: `local.properties`, `app/google-services.json`, `app/build/`.

## Gotchas (quick list)

- A hidden tab may or may not have a view. A tab fragment method called from the activity must not touch the view directly: keep the request in the ViewModel and handle it once the tab is shown (see the cross-tab actions above).
- `data.MemoryFragment` (entity) vs `fragment.MemoryFragment` (screen): the name clash is handled with `import … as MemoryFragmentEntity` in `MemoryFragmentViewModel`.
- `MemoryFragment.title` (entity) is a mutable `@Ignore` field, filled from the parent group at runtime.
- Deleting a group cascades to fragments and media. The undo (`MainActivity.onMemoryDeleted`) calls `MemoryGroupDao.restoreDeletedGroup`, which re-inserts all three in one transaction. Media URI grants are released, and an automatic backup runs, only when the undo Snackbar is dismissed without "Undo": a released grant can't be taken back, so undo would lose the photos. If the process dies while the Snackbar is showing, those grants stay (harmless, but they count toward the 512 cap).
- `MemoryMapApplication.applicationScope` is for short background work that must outlive the screen that started it (the undo and post-delete clean-up). It logs failures instead of crashing.
- Never call the private backup or restore steps outside `performBackup` / `restoreBackup`: those hold the backup lock. The lock is not reentrant, so don't call one from inside the other.
- `Slider.clearOnSliderTouchListeners()` does not remove change listeners; use `clearOnChangeListeners()` before re-adding one in `onBindViewHolder`.
- Debug builds use the default debug keystore, not the release key. For Google sign-in (and a Maps key restricted to Android apps) to work in debug builds, the debug SHA-1 (`./gradlew signingReport`) must be registered for `com.szabolcshorvath.memorymap` in Google Cloud Console. A debug build can't be installed over a release install: uninstall it first.

## Tests

- Robolectric tests use `@ExtendWith(RobolectricExtension::class)` (JUnit 5).
- DAO tests run on Room under Robolectric (`MemoryGroupDaoTest`, `RestoreCompatibilityTest`) and get the DAOs from the database, as the app does (`db.memoryGroupDao()`).
- `RestoreCompatibilityTest` builds a database for every schema version a backup can have (6 to `DB_VERSION`) from `app/schemas` (`SchemaDatabases`) and runs it through the restore steps. A new `DB_VERSION` is picked up automatically; it needs the exported schema JSON. Keep this test passing: it is what guarantees old backups stay restorable.
- No dedicated per-migration or hashing tests yet (`TEST-1`, `TEST-2`).
- UI tests (`app/src/androidTest`, JUnit 4) drive the real app with UI Automator. They run locally on one dedicated emulator, `MemoryMap_UI_Tests` (API 37 with Google Play, signed in once), with `scripts/ui-tests.sh` (the whole suite) or `scripts/ui-tests.sh "MapTest|TimelineTest"` (some classes), in bash (Git Bash on Windows). The script targets that emulator by name through `ANDROID_SERIAL`, so no other device is touched; AGP's own `--serial` option crashes with an `UnsupportedOperationException` (in 9.4.1 and 9.5.0). How to set the emulator up again, and why it must be signed in to Google Play: [docs/ui-tests.md](docs/ui-tests.md). They cover every screen and user flow, apart from a few things left out on purpose: save errors that can't be caused (a full disk, a broken database), Google's own place search screen and the map's tiles in dark mode.
  - Google Play services downloads Google's latest map renderer only on a device set up with Google Play. Without it the map falls back to the legacy renderer, which doesn't support the app's markers and sometimes draws nothing, so the map tests fail. `map/MapRendererTest` fails first in that case. This is why the Gradle managed emulators (`pixel6Api35`, `pixel6Api37`, fresh every run) and CI aren't used for the UI tests any more; the managed devices stay configured for the hand-started CI workflow.
  - To run only some test classes with Gradle directly, pass a regex: `-Pandroid.testInstrumentationRunnerArguments.tests_regex=".*(TimelineTest|MapTest).*"`. A comma-separated `class` list runs only its first class.
  - The results table (`.github/scripts/UiTestSummary.java`, run with the JDK, no other tools needed) is printed by the script and shown on the CI job's summary page, with an annotation per failed test; a failed CI run also uploads the HTML report, the screenshots and every test's logcat as an artifact.
  - The API 37 emulator now and then loses a test: it starts, but no result comes back, and Gradle doesn't count it as a failure. The summary lists such tests with a warning ("without a result"); rerun them, because they weren't checked.
  - The Maps key only accepts registered signing keys, so CI signs the debug build with the debug keystore from the `DEBUG_KEYSTORE_BASE64` secret; without it the map doesn't load and the location picker tests fail.
  - API 37 is the targetSdk. API 35 stands in for minSdk 34: every API 34 emulator image (including the Play Store ones) ships Google Play services 23.18 from 2023 and can't update it, and that version's map renderer crashes on the app's advanced markers. Real Android 14 phones keep Play services current, so this is an emulator limit, not an app bug. Testing on Android 14 needs a real device or Firebase Test Lab.
  - ⚠️ Every test starts from a fresh install: the Test Orchestrator clears the app's data first (`clearPackageData`). Running them on a phone or emulator of your own (`connectedDebugAndroidTest` without `ANDROID_SERIAL`, which runs on every connected device) wipes the debug app's memories there: use the script.
  - `MemoryMapTestRunner` puts fakes into `AppServices` before the app starts (`FakeAccountService`, `FakeBackupStorage`, `FakeMediaPicker`, `FakeLocationService`, `FakePlaceSearch`), so no test reaches a Google account, opens the system photo picker or Google's place search, or depends on the emulator's location, and turns off Firebase collection. `FakeMediaPicker` returns the photos a test set in `nextPick` (for example from `TestData.galleryPhoto`) at once. `FakeLocationService` says the phone is where `TestData.phoneAt` put it, and nowhere (location off) by default. `FakePlaceSearch` returns `nextPick` as the searched and chosen place (null: the user left the search). Location access itself stays Android's: `TestData.grantLocationAccess` grants it, or a test answers the real system dialog (`LocationAccess`).
  - `MemoryMapAppRule.launch()` starts the app the way its launcher icon does. `simulateProcessDeath()` turns on "Don't keep activities", leaves the app and returns to it, and checks that Android rebuilt the screens from their saved state: their ViewModels are cleared as after a real process death, but the process, its database and the fakes keep running. The rule turns the setting off again before and after every test.
  - Tests are grouped by what they cover: `navigation/` (moving between screens, rotation, process death), then one package per screen (`timeline/`, `memory/`, …) for its own flows, `location/` for the "my location" flows on the map and in the location picker, and `edge/` for edge cases across the app (long texts, a large database, dark mode: `MemoryMapAppRule.useDarkMode`). `MemoryMapAppRule.goOffline` turns off Wi-Fi and mobile data, and `useAnimations` turns animations back on for a test that watches one (the test phones run with them off, so an animation ends at once: `scripts/ui-tests.sh` turns them off on the test emulator, since Gradle's `animationsDisabled` only turns off window animations there), and `allowTimeToTakeAction` sets Android's "Time to take action", so a message with an action (Undo) stays long enough on a slow emulator; like dark mode, the rule undoes these after the test (and waits until the network works again).
  - Add data with `TestData` (it writes through the app's DAOs and DataStore, and adds photos to the gallery) before `MemoryMapAppRule.launch()`. `photoSavedByAnotherApp` adds a photo the way a restored backup brings it from another phone, and puts the file in the gallery as another app (the shell) would, so re-linking finds it only with photo access (the app always sees the photos it saved itself, and the re-link that runs at start can't link it early); `grantMediaAccess` stands in for "Allow all" so no system permission dialog appears. Tests that answer Android's own permission dialog use `PermissionDialog`. `colorPresets` sets the colour presets instead of the defaults the app adds on its first start. `trip`, `fragment`, `markerColor`, `markerClustering` and `defaultMapFilter` set up the map tests. `galleryVideo` adds a five-second video of one colour, which `TestVideos` encodes on the phone. `photoTakenAt` adds a gallery photo with a chosen date taken (EXIF), and `missingPhoto` a memory photo whose file is gone, for the missing-photo sheet (optionally with a stored hash or thumbnail). Photos of one colour all have the same perceptual hash, so look-alike tests use `TestData.Stripes`. `awaitStoredThumbnails` waits for the start-up backfill. Test photos are plain colours (`photo(…, rightHalf = …)` gives the right half another colour, to see a zoom), and the screen objects tell them apart by reading the screen's colours (`ScreenColors`), since every thumbnail reads "Open photo". The map opens on a view of Europe and Africa, so `TestData.Place` has cities there. When a test fails, the rule saves a screenshot and the screen's element tree (`<Class>.<test>.png` and `.xml`, via `TestStorage`); Gradle copies them to `app/build/outputs/connected_android_test_additional_output/` (`managed_device_android_test_additional_output/` on the managed emulators, where API 37 writes them but Gradle doesn't copy them off); every test's logcat is collected too.
  - Only the screen objects (`screens/`) look elements up: by text, content description or hint, and by resource id only where nothing visible names the element. Tests never look elements up themselves, so a screen that moves to Compose changes only its screen object. Give new icon-only controls a content description.
  - `screens/` has one file per screen object (`MapScreen.kt`, `MemoryScreen.kt`, …; `Dialogs.kt`, `Messages.kt` and `Keyboard.kt` for the system's dialogs, messages and keyboard). Steps across several screens that many tests take (open a memory from the timeline, edit it, pick a spot on the map) are in `Flows`. Wait with `Ui.waitUntil`, or `Ui.eventually` to read a value until it matches (its last value goes into the failure message), instead of writing a loop; map markers are read with `mapMarkerTitles()` / `mapMarkerTitle()`, which accept both renderers' descriptions.
