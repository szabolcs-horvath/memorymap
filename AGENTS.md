# AGENTS.md — Memory Map

Guide for AI agents and new contributors. Read this before changing code.
Known problems and planned improvements are tracked in [REVIEW_FINDINGS.md](REVIEW_FINDINGS.md) by ID (for example `BUG-3`).
Check that file before "fixing" something that looks odd: it may already be catalogued, with a suggested fix. When you fix one, add a **Status** line to it and update its heading marker and index row (see the top of that file).
Database and schema rules live in `app/src/main/java/com/szabolcshorvath/memorymap/data/AGENTS.md`.
What device logs and emulator tests showed about media re-linking, and why its rules are what they are, is in [docs/media-relinking.md](docs/media-relinking.md).

## What the app is

**Memory Map** is a single-module Android app (Kotlin; Jetpack Compose, moved from XML Views one screen at a time, then the shell around them) for saving personal "memories" on a map.
- A **memory** (`MemoryGroup`) has a title, description, location, date range (or all-day), a marker colour (HSV), photos and videos, and optional **fragments**.
- A **fragment** (`data/MemoryFragment`, a Room entity — not an Android Fragment) is an extra location inside a memory, with an optional date range and its own colour. Its title comes from its group.
- Screens: **Map** (clustered markers, date filter, colour statistics), **Timeline** (search, grouped by day), **Add/Edit** memory, **Settings** (Google sign-in, Drive backup and restore, colour presets, map preferences, re-link media, send logs). There is also a memory detail pager and a full-screen media viewer.
- All data is local (Room). Google Drive (`drive.file` scope) is used only for zip backups of the database file.

## Build and run

Local setup needs files that are **not** in git:
- `local.properties` — copy `local.properties.template`.
- `app/google-services.json` — the Firebase config (ignored by git).

> ⚠️ `local.properties` also holds the release signing passwords. `app/build.gradle.kts` reads only the keys it needs: `MAPS_API_KEY` goes to a manifest placeholder and `OAUTH_WEB_CLIENT_ID` to `BuildConfig`. To add a new value, wire it up explicitly in the same way. Never expose the whole file (for example with the Maps Secrets Gradle plugin), and never log `BuildConfig` fields.

- Without `MAPS_API_KEY` the map doesn't load and place search is turned off (tapping the map still works).
- Without `OAUTH_WEB_CLIENT_ID` the build still succeeds, and sign-in says it isn't set up.
- `minSdk` is 34 (Android 14), the oldest version any user has. Code needs no version checks or fallbacks for older Android versions.
- Robolectric-based tests (`ColorUtilTest`, `MemoryGroupDaoTest`, …) run against `targetSdk 37` with Robolectric 4.17 (older versions could not start them). They need JDK 21 or newer.
- CI runs the unit tests and lint (`tests.yml`, JDK 21, which Robolectric needs for Android 15 and newer), and Detekt (`detekt.yml`) on every push and PR to master, and each fails the check. The UI test workflow (`ui-tests.yml`) runs only when started by hand: CI's fresh emulators lack Google's latest map renderer (see Tests). Run `./gradlew testDebugUnitTest detekt lintDebug` locally before pushing, and the UI tests (`scripts/ui-tests.sh`, see Tests) when a change touches the UI.
- Detekt only reports issues that aren't in `config/detekt/baseline.xml`. Fix new issues instead of adding them to the baseline; regenerate it (`./gradlew detektBaseline`) only after fixing listed ones, so they don't come back unnoticed.
- Workflow actions are pinned to a commit, with the version in a comment (`uses: actions/checkout@<sha> # v7.0.1`). Dependabot (`.github/dependabot.yml`) opens one PR a week that updates them all; to update one by hand, look up the commit of the new version's tag and change both. The Gradle wrapper checks the distribution's checksum (`distributionSha256Sum`): upgrade Gradle with `./gradlew wrapper --gradle-version <version> --gradle-distribution-sha256-sum <sum>`, taking the sum from Gradle's published `.sha256` file for that version.

## Architecture

### Navigation (`ui/shell/`, phase 2 of the Compose shell)
- `MainActivity` shows `AppShell` and runs the start-up checks. There are no fragments. `AppShell` is Material 3's navigation suite, built from its parts (`NavigationSuiteScaffoldLayout` and `NavigationSuite`, as `NavigationSuiteScaffold` does) only so the rail can have Material's narrow 80 dp width: a short navigation bar, or a collapsed wide navigation rail when the window is wide or short (a phone in landscape), none while the media viewer or the location picker shows (a tab tapped over the picker would close it and lose the spot). Where the app is lives in `ShellViewModel` (the tab and the screens over the tabs, kept for process death); what screens ask of the shell goes through `ShellActions`.
- The tabs are drawn by `TabHost`, not by Navigation 3. A tab is composed the first time it is shown and then stays composed, so it comes back as it was left and the map isn't rebuilt; only the selected tab is laid out and drawn (fading through on a switch). A hidden tab's lifecycle is capped at `STARTED` and its Back handlers are off (its own `NavigationEventDispatcher`). Its `rememberSaveable` state is kept by tab. After the activity is recreated, only the shown tab is composed again (`ShellViewModel.onActivityRecreated`). The keyboard is closed whenever a tab is switched or a screen opens over it.
  - A hidden tab keeps collecting its flows (they run while `STARTED`), so it stays up to date. Anything the user should see happen (a scroll, a flash, a camera move, a message) waits until it is `RESUMED`.
  - The tabs' ViewModels belong to the activity (`TabViewModels`), so the shell can hand a tab a request whether or not it is composed.
- The screens over the tabs are a Navigation 3 back stack of `Detail` keys in a `NavDisplay` above the tabs: the memory pager (`MemoryPagerRoute`, a `HorizontalPager`), the media viewer, the location picker over the Add tab, and the missing-photo sheet (`BottomSheetSceneStrategy`, a modal bottom sheet over the memory). Each entry has its own ViewModels and saved state while it is open (the saved-state and ViewModel-store decorators); a screen gets only ids in its key, and loads the rest itself. They slide in, slide out on Back, and follow the predictive Back gesture. The stack starts with `Detail.None`, which draws nothing, so the tabs show through; while a screen covers them they are hidden and paused, and they show again as soon as it starts to leave.
- Cross-tab actions (show on map/timeline, edit) go through `ShellActions`: it selects the tab and calls a `request…` method on the tab's ViewModel (`requestFocusOnMemory`, `requestScrollTo`, `requestEdit`). The ViewModel keeps the request and the tab handles it once it is shown (Edit as soon as the form is composed, since filling a hidden form shows nothing). A request stays pending until handled, and a newer one replaces it.
- Back: a screen over the tabs closes first; then a tab other than the Map goes to the Map; on the Map, Back leaves the app.
- Messages over the tab bar (the undo after a delete, the start-up offer of media access) are the shell's Compose snackbars.

### Data access
- Screens (composables, the shell, `MainActivity`) never touch the database or a DAO: they call their ViewModel, which calls `MemoryRepository` (memories, media, fragments, thumbnails, grant release) or `PresetRepository` (colour presets) in `data/`. Their writes schedule the automatic backup themselves and may be called from the main thread.
- `AppContainer` builds the database, the repositories and `BackupManager` once per process (`MemoryMapApplication.container`, or `context.appContainer`). A ViewModel that needs one takes it in its constructor and has a `Factory`; a tab's is created by the activity (`TabViewModels`), a screen over the tabs creates its own with `viewModel(factory = …)` in its Navigation 3 entry (a factory function such as `MemoryViewModel.factory(memoryId)` when it needs an id). Tests build a ViewModel with a repository on an in-memory database (`SaveMediaTest`).
- Code outside the UI (re-linking, `MissingMedia`, the details backfill, backups, the relink diagnostics) still opens the database with `MemoryMapDatabase.getDatabase`, the same instance.

### Compose
- The UI is all Compose (moved from XML Views one screen at a time, ARCH-10), one package per screen with its ViewModel: the Timeline (`ui/timeline/`), Settings (`ui/settings/`), the memory pager, its pages and the missing-photo sheet (`ui/memory/`), the media viewer (`ui/media/`), the Add/Edit form (`ui/add/`; the marker colour's swatches and sliders are shared with Settings in `ui/color/`), the location picker (`ui/location/`), the Map (`ui/map/`), and the shell around them (`ui/shell/`, see Navigation). The app has no Views of its own, apart from what libraries bring (the map).
- A screen's ViewModel exposes one immutable `StateFlow<XUiState>` and takes intents; the composable gets the state and lambdas, not the ViewModel. A request from the shell (`requestScrollTo`) goes into that state, and the composable handles it once its lifecycle is `RESUMED` (the tab is shown).
- The theme is `ui/theme/MemoryMapTheme`: the colours of `ui/theme/Color.kt` (from Material Theme Builder: light, dark, and the medium and high contrast versions it picks from the phone's contrast setting, following a change at once), with Compose's own Material 3 shapes and type scale. Use `MaterialTheme.colorScheme` and `typography`, never fixed colours; the one colour Material 3 has no role for is `MaterialTheme.success`. The XML theme (`res/values/themes.xml`) only gives the window its background until Compose draws.
- Give the root `Modifier.semantics { testTagsAsResourceId = true }`, so UI Automator sees the test tags as resource ids. Content in a window of its own (a dialog, the Timeline's expanded search) needs it again. A Compose list reports itself as a plain `View`; `Ui.scrollTo` takes it for the page when it offers to scroll up or down. Compose exposes a text field's placeholder as text inside the field, not as its hint, so screen objects find a Compose text field by its tag. A tab or a button made of an icon and a label (the tab bar, a snackbar's action) is one focusable element with its label as a text element inside it: match the element by that child, or tap the label itself.
- Material3 is pinned ahead of the Compose BOM (`composeMaterial3` in `libs.versions.toml`): the BOM takes only stable releases, and Material 3 Expressive's button groups, wavy progress indicators and segmented list items (`SegmentedListItem`) came in 1.5. Move back to the BOM's version once it has 1.5 (BUILD-5). Lists (the Timeline, the backups) use `SegmentedListItem` with `ListItemDefaults.segmentedShapes`, filled with `surfaceContainer` on the page's surface, 4 dp apart. A setting of its own is a standalone item instead (all corners round, 8 dp apart, keeping its shape when switched on): settings that only share a section aren't a list.
- The Timeline searches with Material 3's `TopSearchBar` plus `ExpandedFullScreenSearchBar`: the collapsed bar only opens the expanded search, where the typing happens (since Material3 1.5 the collapsed bar shows no keyboard). Don't build a search bar of your own.
- Libraries the moved screens use: Google's Compose map (`maps-compose`: `GoogleMap` with `contentPadding` for the bars over it, advanced markers, which need the map id `R.string.map_id`; the Map's pins are grouped with `maps-compose-utils`' `Clustering` and drawn by the app's own `ui/map/MarkerRenderer`), drag-to-reorder in lazy lists and grids with `sh.calvin.reorderable` (the memory page's photos and fragments), zoomable photos with telephoto (`ZoomableAsyncImage`, which loads sharper tiles of the file as it zooms), and videos with Media3: ExoPlayer and its Material 3 `Player` with its own controls (`media3-ui-compose-material3`; its progress slider needs `@OptIn(UnstableApi::class)`). Don't build a player's controls of your own.
- `MainActivity` sets `windowSoftInputMode="adjustResize"`: left unset, Android resizes the window for the keyboard only on a screen with a View scroll container, and pans it over a Compose list (the tab bar then disappears under the keyboard). The shell moves up for the keyboard (`windowInsetsPadding(WindowInsets.ime)`); a screen doesn't pad for it again.
- The app is edge to edge: the shell pads for nothing but the keyboard, and each screen keeps clear of the system bars and the camera cutout itself. A screen with a top app bar lets the bar pad for the status bar (don't pass it `WindowInsets(0)`) and pads its content with `WindowInsets.safeDrawing.only(Horizontal + Bottom)`. The Map and the location picker draw the map under the bars and pad only their controls; the map's `contentPadding` needs the numbers, so it reads them from `ui/common/SafeArea` (`track` on the root, `mapPadding` inside). Use `windowInsetsPadding` rather than reading `WindowInsets` values yourself: it knows what the layouts around it handle already (the tab bar pads for the navigation bar below it, the rail for the cutout beside it), the raw values don't.
- A screen's look follows Material 3 Expressive (https://m3.material.io/ is the source of truth, with idiomatic Android and Compose conventions) and Compose's defaults: before redesigning one, review it against them and agree with the user what to adopt. Compare screenshots for regressions (something missing, wrong colours, a broken layout), never chase pixel offsets.

### State
- Screen ViewModels mostly hold plain `var` fields: UI state survives rotation but not process death. The exceptions are the Add form's draft (with the memory it edits) and the location picker's picked spot, which are kept in `SavedStateHandle`.
- The Add tab is both "new memory" and "edit memory". `AddMemoryViewModel.hasUnsavedChanges` compares the form with how it was when last cleared or loaded for editing (call `markUnchanged` after filling it). An Edit request asks before it replaces unsaved changes (for the memory already being edited it keeps them), and switching to another tab closes an edit that has no changes (`closeUnchangedEdit`). A new field that a save stores must also go into `FormContent` (`ui/add/FormContent.kt`, with its Bundle code), or changing it won't count as a change and process death will lose it. Every change goes through an intent of the ViewModel, which then publishes `AddFormUiState` (`publish`). The text fields keep the text as typed (`rememberSaveable`) and start again from the ViewModel when `formVersion` changes (the form was cleared or filled for editing, also by a save that finished on another tab). A save result is handled only while the tab is shown: one that finishes on another tab clears the ViewModel at once, and the kept form shows it when the tab is shown again.
- Preferences: a single DataStore named `"googleAuthDatastore"` (it holds all app prefs, not just auth). Keys and defaults are in `util/PreferencesKeys.kt`; the default map filter is in `util/DateFilterOption.kt` (stored by enum `name`).

### Media handling and re-linking (the evidence behind it: `docs/media-relinking.md`)
- Picked media keep their **photo picker URI**, with `takePersistableUriPermission` (survives reboots, no `READ_MEDIA_*` needed). Android caps persisted grants at 512 and drops the oldest beyond that, so call `LocalMediaUtil.releaseUriGrantsIfUnused` when media is removed or re-linked to another URI. The Add form does it for photos picked in it that leave the form unsaved (removed, cleared, replaced by an edit), but never for media loaded for editing.
- The Add form opens the photo picker through `AppServices.mediaPicker` (the system's `PickMultipleVisualMedia`), so UI tests can replace it. A screen opens it with `rememberLauncherForActivityResult(AppServices.mediaPicker)`.
- Each `MediaItem` stores `deviceId` (the installation id), `fileSize`, `dateTaken` and `mediaSignature` = `"{size}_{md5(first 4 KB + last 4 KB)}"` (`MediaHasher`). The signature is computed once and kept on later saves; only re-linking to an edited version (below) replaces it.
- Each item also stores what the file was (`MediaDetails`): name, pixel size, MIME type, video length and a perceptual hash (dHash) as columns, and a 128 px thumbnail in `media_thumbnails`, keyed by signature. They are read while the file can be read: when the Add form saves new picks (media kept through an edit copy theirs from the saved rows, never through `FormContent`), when the missing-photo sheet replaces an item, and at start-up for older items (`MediaDetailsBackfill`, which also deletes unused thumbnails, only then). They are shown and used for ranking, never for linking on their own; the hash only orders suggestions ("Looks alike").
- `InstallationIdentifier` lives in `noBackupFilesDir` on purpose, so Auto Backup and device transfer don't copy it. Don't move it back into DataStore.
- An item needs re-linking if `deviceId != installationId` or `!isMediaValid` (metadata-only check). `LocalMediaUtil.verifyAndFixMediaItems` matches MediaStore candidates by exact size + signature and updates only `uri` and `deviceId` (`updateMediaLink`), and only while the row still has the URI and signature the run read (a restore during the run can reuse ids). If the signature finds nothing, `EditedPhotoRule` handles a photo edited in place after it was picked: it takes the MediaStore file whose id is in the item's local photo picker URI, if the item was saved by this installation and the file is of the same type with the same date taken to the millisecond, and the item then also takes that file's size and signature. Its old URIs' grants are released if no item uses them. It runs on cold start, after a restore, and from the "Re-link" buttons (which share `ui/common/RelinkRequester`: it asks for media access first when the app lacks full access), always through `MediaRelinker.relink` (never call it directly): runs happen one at a time in `applicationScope`, so they outlive the screen, and requests made during a run share the next one. Each run checks every item again and returns how many are still missing; `hasMissingMedia` answers from the results it cached, so only new or changed items cost a query. Afterwards `deduplicateMediaItems` removes items of one memory that now point to the same photo (same signature), closes the `order` gaps and releases unused grants.
- Never "sweep" all persisted grants that the current database doesn't reference: after restoring an older backup, a newer backup may still need them. Release only the grants of media you just removed (`releaseUriGrantsIfUnused`).
- The "Send logs" zip is written to `cacheDir/logs/`, the only folder the `FileProvider` shares (`res/xml/file_paths.xml`). Keep anything else (backup temp files) out of it.
- "Send logs" also adds `relink_diagnostics.txt` (`RelinkDiagnostics`): why each unlinked item needs re-linking and which files on the phone are near it, with sizes, dates, owners and signatures. It is built when the logs are sent (re-link runs don't pay for it), only reads, and writes its own failure into the file so the logs still go out. Its checks mirror `needsRelink` and the matching rules (signature and `EditedPhotoRule`), so keep them in step.
- Media from another device is shown as an error tile (type, size, date) and is not loaded.
- Tapping a tile whose item needs re-linking opens the missing-photo sheet (`MissingMediaSheetRoute`, a `Detail.MissingMedia` entry over the memory with the item id in its key) instead of the media viewer. With full media access it re-links first, then suggests files of the same type taken around the same time (`NearbyMedia`). The user can use one, choose another photo or remove the item (`MissingMedia`). A replacement is not a re-link: `MediaItemDao.replaceMedia` writes the new file's URI, device, type, signature, size and date, keeping the item's id and place.

### Backup and restore (`backup/BackupManager.kt`, `ui/settings/`)
- Backup: `PRAGMA wal_checkpoint(TRUNCATE)`, copy the database file (and the WAL if not empty) while holding a write transaction (a consistent snapshot), check the copy with `MemoryMapDatabase.withCheckedCopy` (the same open, migration and integrity checks a restore runs), then zip `database.sqlite` (+ `-wal` if still present) + `metadata.json` (`BackupZip`) and upload to the Drive folder "Memory Map Backups" as `MemoryMap_{Automatic|Manual}_Backup_<yyyyMMdd_HHmmss>.zip`. Older backups also contain `-shm`; restore ignores it.
- **Automatic backups** run in the background through WorkManager (`backup/AutomaticBackups.kt`). Every write (save, reorder, preset changes, undo, a final delete, a missing photo replaced or removed) calls `AutomaticBackups.schedule(context)`, which returns at once; for the screens' writes the repositories do it. It enqueues unique work (`ExistingWorkPolicy.REPLACE`), so a burst of changes leads to one upload 15 seconds after the last one, only with a network, and it survives the screen and the process. `AutomaticBackupWorker` calls `BackupManager.runAutomaticBackup`, which skips when nobody is signed in and otherwise runs `performBackup`. Network and Drive server errors are retried (up to 5 attempts, exponential backoff); missing consent and other errors are not. Settings shows the state as a small inline line (`AutomaticBackups.status`) and refreshes the backup list when a run finishes. Never call `performBackup` for automatic backups directly. Old backups are still never pruned (`DATA-4`).
- Backup and restore share one process-wide `Mutex` in `BackupManager`, so they run one at a time (callers wait for the running one). Each run uses its own temp directory in `cacheDir` (`BackupTempFiles`); leftovers from killed runs are deleted when the next run starts.
- Old backups are never deleted by the app (pruning was deliberately postponed, `DATA-4`). `listBackups` pages through all of them.
- `listBackups` returns a `Result`: a failure is never an empty list, which would look as if the backups were gone. Settings keeps the list it showed and says why it couldn't refresh (`DriveProblem`: no connection, Drive not responding, access lapsed, other), with "Allow access" when access lapsed (the consent screen the failed call came with, or the app's usual Drive consent). Automatic backups decide what to retry with the same `DriveProblem`.
- Restore: download, extract only the known entries (`BackupZip`), check `metadata.json` and `database.sqlite` exist, reject backups from a newer database version (`BackupCompatibility`), open the extracted copy with `MemoryMapDatabase.withCheckedCopy` (migrations, schema and integrity checks; rejects a file SQLite would have to create from scratch), read every row (`DatabaseContents`), then replace the live database's contents in one transaction (`DatabaseContentsDao.replaceAll`). The live database is never closed or swapped, Room's Flows pick up the new data, and any failure leaves the current data untouched. The UI then re-links media with whatever media access was granted (the restore never waits for it) and offers full access if photos are still unlinked.
- Android's own Auto Backup and device transfer exclude the database and the DataStore (`res/xml/data_extraction_rules.xml`): memories come back only through the Drive backups.
- Auth: sign-in stores the email in DataStore (`USER_EMAIL_KEY`). Sign-in and Drive consent go through `AppServices.accounts` (`GoogleAccountService`: Credential Manager and `AuthorizationClient`), and Drive file calls through `AppServices.backupStorage` (`DriveBackupStorage`). One stack does both: Credential Manager says who the user is, and `AuthorizationClient` grants the `drive.file` scope for that account and gives the access token every Drive call sends (`GoogleAccountService.driveAccessToken`, which Play services caches and renews). When access has to be allowed first, the token request throws `DriveAccessNeededException` with the consent screen; a token Drive rejects (401) is cleared and replaced once. Always reach them through `AppServices` at the time of the call, never directly: UI tests replace both with fakes, so a test never touches a real account.

## Conventions

- Run `./gradlew detekt` before committing (CI fails on new issues). `MagicNumber` is active, which is why numbers live in named `private const val`s in a `companion object`.
- Each screen has a route composable (`MapRoute`, `MemoryRoute`, `AddMemoryRoute`, `SettingsRoute`, …) that takes its ViewModel and does what needs the activity: activity result launchers (`rememberLauncherForActivityResult`, which also gets a result that arrives after the activity is recreated), the questions, sign-in. The shell composes it, in a tab or in a Navigation 3 entry.
- The location itself is read through `AppServices.location` (`FusedLocationService`, Google Play services' fused provider), so UI tests can say where the phone is. The location picker's place search goes through `AppServices.placeSearch` (`GooglePlaceSearch`: the Places SDK's search screen and Place Details), so UI tests don't call the paid API. Location access is asked for only when the user taps a "my location" button (`ui/common/MyLocation.kt`: `rememberMyLocationRequester` with `MyLocationQuestions`, used by the map and the location picker), never when a screen opens: first a short explanation, then the system dialog, and once Android no longer asks, an offer to open the app's settings (the denial is kept in DataStore, `LOCATION_PERMISSION_DENIED`). Google's own my-location button is turned off because it only appears once access is granted; both maps use the app's floating toolbar instead (`ui/map/MapToolbar`: zoom in, zoom out, my location, with Google's zoom buttons off too), which floats over the map so the map keeps no room for it. Code that merely uses the location when it is granted (the blue dot, the first zoom, preselecting it in the picker) must not ask.
- Ask yes-or-no questions with `ui/common/ConfirmDialog` (Material 3's `AlertDialog`). Keep whether it is open, and what the answer acts on, in `rememberSaveable` (or the ViewModel's saved state), so it comes back after the phone is turned and after process death.
- On a Compose screen, use Material 3's date, date range and time pickers (`ui/add/FormDates.kt`): which one is open is kept with `rememberSaveable`, so it comes back after a rotation and process death, and the date pickers get a locale with the phone's first day of the week (`WithPhonesWeek`). The range picker (`RangePicker`) is shared with the Map's date filter.
- Firebase Performance is used heavily: `@AddTrace` annotations, `PerfUtil.trace("name") { }`, `RoomDatabase.withTransaction("name") { }` (the traced overload in `PerfUtil`). Trace names are `snake_case` (`<class>_<method>`). Don't put `@AddTrace` on hot or per-item functions (helpers called per marker, per pair or per media item): each call starts a trace.
- Shown text comes from `res/values/strings.xml`: never write it into Kotlin or a layout (a layout's preview text goes in `tools:text`). Counts use `plurals`, and text built from parts uses a pattern with placeholders (`date_range`, `backup_details`), so a translation can reorder it. Text that is stored or looked up rather than shown (the Drive folder name, backup file names, keys) and the logs stay fixed in code.
- Never show users an exception's class name or message: say what failed and why in words they can act on (for Drive calls, `DriveProblem.reason`), and log the exception, which "Send logs" picks up. Show a place without a name with `util/Coordinates.format` ("47.4979° N, 19.0402° E").
- Show dates and times with `DateTimeFormatterUtil.date`, `time(context, …)`, `dateTime(context, …)` and `twoLineDateTime`: Android's ICU formatter, so they read as in the rest of the phone (its language, digits and calendar, and its 12- or 24-hour clock setting). `java.time` formatters ignore the digits and the calendar, so don't use them for shown text. Weeks start on `firstDayOfWeek()` (`util/PhoneCalendar.kt`): wrap a Material 3 date picker in `WithPhonesWeek`; give a Material 3 time picker `is24Hour = DateFormat.is24HourFormat(context)`. Text that is stored or parsed rather than shown (backup file names and `metadata.json`, the logs, the relink diagnostics) keeps its fixed format: never pass it through these.
- Read colours from `MaterialTheme.colorScheme`, never from `ui/theme/Color.kt`'s schemes directly: the theme picks the one for dark mode and the phone's contrast setting. To change the palette, replace all six schemes with a new Material Theme Builder export, and the window background in `res/values*/colors.xml` with its `background`.
- Generated or local-only files to keep out of commits: `local.properties`, `app/google-services.json`, `app/build/`.

## Gotchas (quick list)

- A hidden tab may or may not be composed. A request for a tab goes to its ViewModel, which keeps it until the tab is shown and handles it (see the cross-tab actions above).
- The map's clustering (`maps-compose-utils`' `Clustering`) gives the cluster manager every pin again whenever the list changes, and the renderer reuses the marker of a pin that comes back equal. So everything a marker shows must be part of its pin's equality, or the marker keeps showing the old value. If the map gets slow with many memories, see PERF-8 for keeping only the changed pins.
- A fragment (`data.MemoryFragment`) has no title of its own. The map shows it under its memory's, wrapped in `Markerable.FragmentMarker`: never change the objects Room emits, other screens share them.
- Deleting a group cascades to fragments and media. The undo (`ShellActions.memoryDeleted`, through `CommonViewModel.undoDelete` and `MemoryRepository.undoDelete`) calls `MemoryGroupDao.restoreDeletedGroup`, which re-inserts all three in one transaction. Media URI grants are released, and an automatic backup runs, only when the undo Snackbar is dismissed without "Undo": a released grant can't be taken back, so undo would lose the photos. If the Snackbar is cut short (another delete, the activity recreated), the delete is final too. If the process dies while the Snackbar is showing, those grants stay (harmless, but they count toward the 512 cap).
- `MemoryMapApplication.applicationScope` is for short background work that must outlive the screen that started it (the undo and post-delete clean-up). It logs failures instead of crashing.
- Never call the private backup or restore steps outside `performBackup` / `restoreBackup`: those hold the backup lock. The lock is not reentrant, so don't call one from inside the other.
- Debug builds use the default debug keystore, not the release key. For Google sign-in (and a Maps key restricted to Android apps) to work in debug builds, the debug SHA-1 (`./gradlew signingReport`) must be registered for `com.szabolcshorvath.memorymap` in Google Cloud Console. A debug build can't be installed over a release install: uninstall it first.

## Tests

- Robolectric tests use `@ExtendWith(RobolectricExtension::class)` (JUnit 5).
- DAO tests run on Room under Robolectric (`MemoryGroupDaoTest`, `RestoreCompatibilityTest`) and get the DAOs from the database, as the app does (`db.memoryGroupDao()`).
- `RestoreCompatibilityTest` builds a database for every schema version a backup can have (6 to `DB_VERSION`) from `app/schemas` (`SchemaDatabases`) and runs it through the restore steps. A new `DB_VERSION` is picked up automatically; it needs the exported schema JSON. Keep this test passing: it is what guarantees old backups stay restorable.
- No dedicated per-migration tests yet (`TEST-1`).
- A Robolectric test that saves through a ViewModel (`SaveMediaTest`) builds it with a `MemoryRepository` on an in-memory database, sets `Dispatchers.Main` to the test's main looper (Robolectric gives every test a new one, and `Main` would keep the first test's) and starts a test WorkManager (`WorkManagerTestInitHelper`), because a save schedules an automatic backup. Don't start a Firebase app in unit tests: Crashlytics then contacts Google's servers. `PerfUtil.trace` runs its work untraced without one.
- UI tests (`app/src/androidTest`, JUnit 4) drive the real app with UI Automator. They run locally on one dedicated emulator, `MemoryMap_UI_Tests` (API 37 with Google Play, signed in once), with `scripts/ui-tests.sh` (the whole suite) or `scripts/ui-tests.sh "MapTest|TimelineTest"` (some classes), in bash (Git Bash on Windows). The script targets that emulator by name through `ANDROID_SERIAL`, so no other device is touched; AGP's own `--serial` option crashes with an `UnsupportedOperationException` (in 9.4.1 and 9.5.0). How to set the emulator up again, and why it must be signed in to Google Play: [docs/ui-tests.md](docs/ui-tests.md). They cover every screen and user flow, apart from a few things left out on purpose: save errors that can't be caused (a full disk, a broken database), Google's own place search screen and the map's tiles in dark mode.
  - Google Play services downloads Google's latest map renderer only on a device set up with Google Play. Without it the map falls back to the legacy renderer, which doesn't support the app's markers and sometimes draws nothing, so the map tests fail. `map/MapRendererTest` fails first in that case. This is why the Gradle managed emulators (`pixel6Api35`, `pixel6Api37`, fresh every run) and CI aren't used for the UI tests any more; the managed devices stay configured for the hand-started CI workflow.
  - To run only some test classes with Gradle directly, pass a regex: `-Pandroid.testInstrumentationRunnerArguments.tests_regex=".*(TimelineTest|MapTest).*"`. A comma-separated `class` list runs only its first class.
  - The results table (`.github/scripts/UiTestSummary.java`, run with the JDK, no other tools needed) is printed by the script and shown on the CI job's summary page, with an annotation per failed test; a failed CI run also uploads the HTML report, the screenshots and every test's logcat as an artifact.
  - The API 37 emulator now and then loses a test: it starts, but no result comes back, and Gradle doesn't count it as a failure. The summary lists such tests with a warning ("without a result"); rerun them, because they weren't checked.
  - The Maps key only accepts registered signing keys, so CI signs the debug build with the debug keystore from the `DEBUG_KEYSTORE_BASE64` secret; without it the map doesn't load and the location picker tests fail.
  - API 37 is the targetSdk. API 35 stands in for minSdk 34: every API 34 emulator image (including the Play Store ones) ships Google Play services 23.18 from 2023 and can't update it, and that version's map renderer crashes on the app's advanced markers. Real Android 14 phones keep Play services current, so this is an emulator limit, not an app bug. Testing on Android 14 needs a real device or Firebase Test Lab.
  - ⚠️ Every test starts from a fresh install: the Test Orchestrator clears the app's data first (`clearPackageData`). Running them on a phone or emulator of your own (`connectedDebugAndroidTest` without `ANDROID_SERIAL`, which runs on every connected device) wipes the debug app's memories there: use the script.
  - `MemoryMapTestRunner` puts fakes into `AppServices` before the app starts (`FakeAccountService`, `FakeBackupStorage`, `FakeMediaPicker`, `FakeLocationService`, `FakePlaceSearch`), so no test reaches a Google account, opens the system photo picker or Google's place search, or depends on the emulator's location, and turns off Firebase collection. It also has videos played with software decoders (`AppServices.videoDecoders`): the emulator's hardware video decoder fails when an app runs it, while the app keeps the phone's own choice. `FakeMediaPicker` returns the photos a test set in `nextPick` (for example from `TestData.galleryPhoto`) at once. `FakeLocationService` says the phone is where `TestData.phoneAt` put it, and nowhere (location off) by default. `FakePlaceSearch` returns `nextPick` as the searched and chosen place (null: the user left the search). Location access itself stays Android's: `TestData.grantLocationAccess` grants it, or a test answers the real system dialog (`LocationAccess`).
  - `MemoryMapAppRule.launch()` starts the app the way its launcher icon does. `simulateProcessDeath()` turns on "Don't keep activities", leaves the app and returns to it, and checks that Android rebuilt the screens from their saved state: their ViewModels are cleared as after a real process death, but the process, its database and the fakes keep running. The rule turns the setting off again before and after every test.
  - Tests are grouped by what they cover: `navigation/` (moving between screens, rotation, process death), then one package per screen (`timeline/`, `memory/`, …) for its own flows, `location/` for the "my location" flows on the map and in the location picker, and `edge/` for edge cases across the app (long texts, a large database, dark mode: `MemoryMapAppRule.useDarkMode`). `MemoryMapAppRule.goOffline` turns off Wi-Fi and mobile data, and `useAnimations` turns animations back on for a test that watches one (the test phones run with them off, so an animation ends at once: `scripts/ui-tests.sh` turns them off on the test emulator, since Gradle's `animationsDisabled` only turns off window animations there), and `allowTimeToTakeAction` sets Android's "Time to take action", so a message with an action (Undo) stays long enough on a slow emulator; like dark mode, the rule undoes these after the test (and waits until the network works again).
  - Add data with `TestData` (it writes through the app's DAOs and DataStore, and adds photos to the gallery) before `MemoryMapAppRule.launch()`. `photoSavedByAnotherApp` adds a photo the way a restored backup brings it from another phone, and puts the file in the gallery as another app (the shell) would, so re-linking finds it only with photo access (the app always sees the photos it saved itself, and the re-link that runs at start can't link it early); `grantMediaAccess` stands in for "Allow all" so no system permission dialog appears. Tests that answer Android's own permission dialog use `PermissionDialog`. `colorPresets` sets the colour presets instead of the defaults the app adds on its first start. `trip`, `fragment`, `markerColor`, `markerClustering` and `defaultMapFilter` set up the map tests. `galleryVideo` adds a five-second video of one colour, which `TestVideos` encodes on the phone. `photoTakenAt` adds a gallery photo with a chosen date taken (EXIF), and `missingPhoto` a memory photo whose file is gone, for the missing-photo sheet (optionally with a stored hash or thumbnail). Photos of one colour all have the same perceptual hash, so look-alike tests use `TestData.Stripes`. `awaitStoredThumbnails` waits for the start-up backfill. Test photos are plain colours (`photo(…, rightHalf = …)` gives the right half another colour, to see a zoom), and the screen objects tell them apart by reading the screen's colours (`ScreenColors`), since every thumbnail reads "Open photo". The map opens on a view of Europe and Africa, so `TestData.Place` has cities there. When a test fails, the rule saves a screenshot and the screen's element tree (`<Class>.<test>.png` and `.xml`, via `TestStorage`); Gradle copies them to `app/build/outputs/connected_android_test_additional_output/` (`managed_device_android_test_additional_output/` on the managed emulators, where API 37 writes them but Gradle doesn't copy them off); every test's logcat is collected too.
  - Only the screen objects (`screens/`) look elements up: by text, content description or hint, and by resource id (a Compose test tag) only where nothing visible names the element, or for a Compose text field (its placeholder is not its hint). Tests never look elements up themselves, so a screen that moves to Compose changes only its screen object. Give new icon-only controls and sliders a content description (a string resource): `edge/ControlNamesTest` checks every screen (`screens/ControlNames`), so add a step there for a new screen or state.
  - `screens/` has one file per screen object (`MapScreen.kt`, `MemoryScreen.kt`, …; `Dialogs.kt`, `Messages.kt` and `Keyboard.kt` for the system's dialogs, messages and keyboard). Steps across several screens that many tests take (open a memory from the timeline, edit it, pick a spot on the map) are in `Flows`. Wait with `Ui.waitUntil`, or `Ui.eventually` to read a value until it matches (its last value goes into the failure message), instead of writing a loop; map markers are read with `mapMarkerTitles()` / `mapMarkerTitle()`, which accept both renderers' descriptions.
